# v41 — GBM特徴のPFを「v38錨付き調整済み1本」に差し替え(tabular学習)

> **状態: 実装済(未実行)。** ファイル: `v41/create_train_parquet_v41.py` / `v41/train_models_v41.ipynb`。
> ユーザー指示「tabularで学習できるように。特徴量は同じ、使うpfが違うだけ(単体)。素で提出したやつを使う」。

## 仮説
GBM特徴の心臓部であるPF軌跡(pf_ancc/self/nbr系)を、**単体新記録の錨付きPF**(v38 struct×mult30,
LB 8.593 = 提出済みと同一パラメータ)に差し替えれば、tabular全体が底上げされる。
転移ラダー最強の「エンジン改善→GBM特徴」経路(70-100%転移)×「prior入り=転移率≈1.0」の合流。

## 変更点(v28 createからの差分)
- **PF_BANK = ["pfA"] の1本のみ**。pfA = `v38_submit_pack.json` の調整済みbest(mult30 study)。
- smoother に **struct錨(row, mult30)** を挿入(`_v26_pad`/`_v26_smoother_core`/`run_smoother_ext` を
  錨対応化、入力構築3ループで `_attach_anchor`)。**v28本家のcreateは不変**。
- 特徴パイプラインは同一。単バンクなので pf_*_2/3・バンク間特徴(agree/diff/between系)は自然に消える
  (createは `len(pf_runs)>=2` ガード済みで単バンク頑健)。ベースの `pf_ancc` = pfA 出力(alias)。
- 出力: `v41/artifacts_v41/data/train.parquet`。features.json は学習ノートが自動生成。

## 学習(train_models_v41.ipynb = v36のコピー)
- USE_BACKWARD=False(逆方向DAなし。まず錨PF差し替えの純効果を測る)。9モデル(lgb/cb/xgb×3)、
  GroupKFold5、ROW_FRAC=1.0、評価= apply_pp 後 overall(w_pf=0.09 は pfA 由来の pf_ancc に適用)。
- 基準: v28本家 GBM 7.048(pp後)/ v36 DA 7.002(pp+SG, gbm_v36_oof)。
- OOF保存: `gbm_v41_oof.npy`。

## 実行手順

```
python v41/create_train_parquet_v41.py     # GPU: 錨PF3パス(resamp高めで各~20分)+build(1-2h)
# → v41/train_models_v41.ipynb を実行(GBM 9モデル)
```

## 結果(2026-07-09)
- **CV 7.4 = 良い値**(ユーザー判定)。v28本家は**3バンク(pf_1/2/3)で7.048**、v41は**単バンク1本+特徴
  大幅減(pf_*_2/3・agree/diff/between系が消失=特徴1/3以下)で7.4**。**特徴が激減しているのに +0.35 しか
  離れていない = 錨PF1本の情報密度が非常に高い=錨が明確に効いている**証拠。
- **★LB 7.994(CV 7.4, 転移率1.08)**。★重要教訓: **錨(空間prior)をtabularのPF特徴に焼き込むと、
  v36 GR-tabular の増幅転移(0.84)が死ぬ**(転移率が空間prior側の1.1へ引き上げられる)。錨はCVレバー
  (情報密度↑)だがLBでは増幅せず、v41は「特徴減の損 + 増幅喪失」の悪いとこ取りで v36(5.864)に遠く及ばず。
  **錨とGRの増幅転移はトレードオフ** → tabularのLB更新は v36系(GR+DA)が本命、錨路線はCV/純PF側で活かす。

## ★次の一手: 3バンク錨版(v42, 本命)
pf_1/2/3 それぞれに struct錨を足す(= v28と**列完全互換**、agree/diff/between系も全維持)。
特徴数はv28と同じで唯一の差分=錨 → **v28本家7.048を明確に割る見込みが高い**(単バンクで既に肉薄なので)。
create の PF_BANK=[pf_1,pf_2,pf_3] のまま、各バンクの smoother に錨挿入(v41の錨機構を3バンクへ)。計算量3倍(錨PF9パス)。
