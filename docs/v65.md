## self / neighbor 疑似typewell(2026-07-17 追加)
- **`TW_SOURCE` env(tw | self | nbr | self+nbr)を study 単位で固定**し、混合比 `self_mix_w` / `nbr_mix_w`(0.1–1.0)を Optuna が探索。
  両方同時混合可(nbr → self の順に格子へ上書き混合)。
- **nbr 仕様は v47 create と同一**: XY重心 ≤1500ft の train 坑井 最大3本、**2本未満なら typewell フォールバック**
  (train チューニング時は自分自身を除外。test では除外不要)。近傍重心は `train_centroids.json` にキャッシュ。
- **`grid_step` は tw/self/nbr の全格子に共通適用**(self/nbr の (TVT,GR) 点群も同じ刻みで median ビニング)。
  既知の目安: tw 単独は粗め(0.5)が良く(v49)、self/nbr 使用時は 0.2 が最適だった実績 — 探索範囲 {0.2, 0.35, 0.5} 内で Optuna が決める。
- **σ較正は純 typewell に対して実施後に混合**(self で較正すると prefix 自己一致で σ→0 に縮退するため)。
- **ソースの記録**: STUDY 名のデフォルトが `v65_pf_{TW_SOURCE}` になり(ファイル名)、current/best json にも
  `tw_source` フィールドと params 内の `tw_source`/`self_mix_w`/`nbr_mix_w` が入る(ファイル内)。
```bash
TW_SOURCE=self+nbr N_TRIALS=300 .venv/Scripts/python.exe v65/tune_pf_v65.py   # → v65_pf_self_nbr_current.json
```
- 提出ノートも対応済み: PARAM_SETS 各セットの `tw_source` を見て、nbr が必要な場合のみ test 側で train 近傍プールを構築。

## 性格別チューナ(`tune_pf_personality_v65.py`, 2026-07-17 追加)
「性格違いのPF」を量産するための**明示的な探索制限**版。ファイル内の `PERSONALITY = "..."` を変えるだけで
制約と出力ファイル名(`v65p_{性格}[_{tw_source}]_current/best.json`)が切り替わる(env PERSONALITY でも上書き可=テスト用)。

| 性格 | 制約(ピン留め/狭め) | キャラクター |
|---|---|---|
| `smooth_tracker` | jump_prob=0固定 / mom 0.997+ / 低vn・pn / rate_clip小 | 滑らか追従、モード跳びしない保守派 |
| `jumpy_explorer` | jump_prob {0.005..0.05}(**0除外=跳躍必須**)/ jump_std〜30 / 低mom / 高pn | 双峰脱出マシン |
| `anchor_faithful` | **use_anchor=True固定** / mult 5-25(強) | struct信者(tail担当) |
| `anchor_loose` | **use_anchor=True固定** / mult 25-80(弱) | 錨を緩い誘導に留める(旧 anchor_late=ramp遅延を ramp固定化で転用) |
| `sharp_matcher` | gr_power 2.4-3.5 / σ倍率1.2-2.2 / 格子0.2固定 | GR細部を信じてコミット |
| `robust_skeptic` | power 1.2-2.0 / σ倍率2.5-5 / 強平滑 / 粗格子 | 外れGRに鈍感(旧 lk_floor床を固定化で不可→power/σ/平滑/格子で代替) |
| `dip_holder` | 超高mom 0.9995+ / init_rate_std小 / vn小 / rate_clip必須 | 初期dip持続(旧 dip_keeper=rate_target"ir"を固定化で高momに転用) |
| `wide_net` | 粒子 {1200,1600,2400} / init_pos_std 2-8 / 低頻度リサンプル | 大群広網の事後分布派 |

- **錨は宣言制**: use_anchor は性格が宣言し**探索されない**(True の性格では必ず錨が使われる)。錨なし性格では錨系ノブ自体が探索から消える。
- tw/self/nbr は性格の対象外(従来どおり env TW_SOURCE、混合比のみ探索)= 8性格 × 4ソース = 最大32バンクの量産マトリクス。
- best/current json に `personality` / `use_anchor` / `constraints` を明記。params はそのまま submit_pf_v65 に貼れる。
```bash
# ファイル内 PERSONALITY を書き換えて:
.venv/Scripts/python.exe v65/tune_pf_personality_v65.py          # → v65p_{性格}_current.json
TW_SOURCE=self+nbr .venv/Scripts/python.exe v65/tune_pf_personality_v65.py   # → v65p_{性格}_self_nbr_*.json
```

## warm-up(r0初期値, 2026-07-17 追加)
- 両チューナとも **study が空のとき r0_seed32 のパラメータを初期 trial として enqueue**(`warmup_v65.py`)。
  TPE がランダムでなく実績 regime から出発する。
- 探索空間は **pf_engine_v65.py のソースを実行時パース**して取得 → 範囲を編集しても warm-up が追随。
  r0 の値が空間外なら自動スナップ(categorical=最近傍 / float=クリップ)。性格チューナでは**性格制約内に
  丸めた r0**(例: jumpy_explorer では jump_prob 0.002→0.005)が入る。
- 既存 study に後から入れたい場合: `FORCE_WARMUP=1` を付けて起動(次の trial として r0 が走る)。

## fullfield(npz完全不要版, 2026-07-18)
- `submit_struct20_fullfield_v65.ipynb` = **struct場・κ・σ(dd)較正まで全て実行時構築**(train CSV+test既知帯)。
  npz は単なるキャッシュだった(再構築の train 場 12,296点 = npz と完全一致で再実装を証明。構築15秒)。
- livefield 版との違い: **κ/σ を「test増強後の場」の下で LOO 較正し直す**(npz流用は train-only密度の較正値)
  + dataset 添付不要。`INCLUDE_TEST_PREFIX=False` で train-only 再構築の対照実行も可。
- **★LB結果(2026-07-19): 7.963** vs struct20(npz) 7.881 = **+0.082 ほぼ変わらず(微悪化)→ 不採用**。
  ローカルでは行平均|Δ|=0.81ft と場は確かに動いていたが、動きに価値がなかった。
  **test既知情報は prior(struct)側からは価値を生まない** — v31「近傍幾何転写=死、近傍の価値はGR経由のみ」/
  v42「空間だけは死」の LB 再確認(3度目)。合法リークのレバーは **GR/尤度側**に集中する
  (self/nbr=実証済み、次= A test間相互nbrプール)。livefield(点のみ追加)の ablation 提出も不要
  (合計≈0 のため分解しても得るものなし)。npz 不要の実行時構築自体は運用資産として温存
  (`INCLUDE_TEST_PREFIX=False` で従来 struct20 と等価・dataset 添付不要)。
- 戦略メモ(ユーザー): このコンペの本質は「**testの既知情報の合法活用**」— self/nbr が最大実証。未開拓の残り:
  **A=test間相互nbrプール(次の推奨)**/ G=反復相互pseudo-typewell(EM転がし)/ B=eval帯再較正 / C=TTT。
  fullfield の結果により **A/G(GR側)を優先、struct場系の増強は打ち止め**。

## PF 間引き(MD粗化)版(2026-07-14, `pf_dec_v65.py` / `tune_pf_dec_v65.py`)
- 背景: 「予測粒度を MD~10 に粗くすると情報圧縮で効くのでは」(ユーザー案)。**先に相関診断**(`検証/gr_typewell_md_coarsen.py`):
  観測GR×typewell期待GR の坑井別相関は **bin平均で 0.665→0.717(+0.05, 98.7%改善)**。ただし control で判明:
  **その利得は MA(全行保持)で全部取れる**(MA3/5/7 ≈ bin平均 同窓、差~0.001)。しかも **PF tuning は生GR(hgr_smooth_r=0)を
  RMSE最良に選ぶ = MA相関利得は PF RMSE に非転移**(相関=trend一致 ≠ localization)。→ **相関経由の旨味は無し**。
- **残る未探索レバー = decimation(ステップ数削減)そのもの**: MA(平滑)では取れない、解像度を落とさないと出ない効果 =
  ①PF overconfidence 緩和(冗長な相関更新を1/DEC)②速度 ~DEC倍。これを **RMSE 直**で測るのがこの版。
- 実装: 既存 `pf_engine_v65` **無改造**。`pf_dec_v65.make_inputs_dec` が make_inputs 出力(md/z/gr/anc/ancs)を
  MD=DEC で bin集約(GR は常に mean=denoise)→ PF → **予測軌跡を full_md に補間して全解像度で採点**
  (= 本物の MD-1 メトリク = current v65 と直接比較可)。**別 study・別 db(`optuna_dec.db`)で current v65 に非干渉**。
```bash
DEC=10 .venv/Scripts/python.exe v65/tune_pf_dec_v65.py     # study=v65dec10_{prior}_{tw}, warmup r0+st20
# AGG=sub で純間引き(md/z集約を中央点に)。GRは常にbin平均。
```
- **判定**: dec10 best(全解像度, 別seed)が **current v65(MD-1)best を維持/改善するか**。改善なら decimation 固有効果が実在
  (+~10倍速)。悪化なら「粗化は照合を落とすだけ」。スモーク(30坑井2trial)で端到端・全解像度RMSE妥当を確認済。
- **★実測(2026-07-14)**: MD-10 チューニングで **7.63 到達**(**grid 0.5 を最良に発見**=v49「粗格子が良い」の再現。間引き+粗格子が MD-10 の個性)。current v65(MD-1, 8.2)と同等〜やや上、+約10倍速。

## 合成尤度PF(composite-likelihood, `pf_engine_multi_v65.py` / `tune_pf_multi_v65.py`, 2026-07-15)

- **狙い**: 現状の self/nbr 合成はテンプレート**平均**(`make_inputs` の blend=平均禁, [[analog-competitions-research]])しかない。
