# v10

> 逆方向パーティクルフィルタ特徴の実験。v9 をベースに、順方向PF軌跡の終端から
> 逆方向にPFを走らせた TVT 軌跡を特徴量に加え、LightGBM の CV で効果を検証する。
> 最終更新: 2026-06-28

## 仮説
- 順方向PF(評価ゾーンを手前→終端へ)に加え、終端→手前へ逆方向にPFを走らせた軌跡を
  特徴に足すと、両方向の情報・両者の食い違い(=不確実性)が手がかりになり精度が上がるのでは。

## 実験設計
- PFは **pf_1 / pf_2 / pf_3 の3セット**(`N_PF_SETS=3`)。各セットで順方向 **`n_seeds=32`**、
  逆方向は各順方向終端から **4本ずつ(32×4=128本)**。
- 順方向は v9 と同じく suffix `_1/_2/_3`(+ set1 のエイリアス無印)と PF間コンセンサス特徴を生成。
  逆方向・比較も各セットごとに suffix 付きで生成。
- **PF以外の特徴は v9 をそのまま継承**(v9 の `build_well` を exec で再利用)。
- **順方向・逆方向PF特徴はどちらも GPU(PyTorch)生成**(シード変動はOKの粒度)。
  順方向GPUアンサンブルを v9 build_well に注入し、v9 の順方向PF特徴定義で特徴化(CPU順方向PFは不使用)。
  `pf_z` のみ v9 のまま CPU。
- 逆方向は **32本をアンサンブルして単一の `bpf_ancc`(+std)** にする。
  ★ seed ごとの列は作らない(LightGBM が無意味な seed 軸で分岐しないため)。

## 列の命名と3実験
- 順方向(v9)特徴: v9 のまま(`pf_ancc`, `pf_*`, 非PF特徴, `target` ...)
- 逆方向特徴: 接頭辞 `bpf_`(各PFセットで suffix 付き。例 `bpf_ancc_1`, `bpf_1_gr_abs_min` ... + set1エイリアス `bpf_ancc`)
- 比較特徴: 接頭辞 `cmp_`(各PFセットで `pf_ancc{s}` vs `bpf_ancc{s}` の差分・GR当てはまり比較等)
- 3実験は列接頭辞で選択:
  1. 順方向のみ(=v9): `bpf_` / `cmp_` を除外
  2. 順方向+逆方向: `cmp_` を除外
  3. 順方向+逆方向+比較: 全列

## 逆方向PFの物理(モデリング上の選択・調整可)
- 評価ゾーンを終端→手前に辿る。MD反転(`md_bwd = -md[::-1]`)で間隔を保持。
- 初期位置 = 順方向終端 pos(=TVT+Z)、初期レート = -(順方向終端 rate)(向き反転)、初期分散で4本に分岐。

## LB追試まとめ(逆方向はどの設定でもv9未満)
| 設定 | LB |
|---|---|
| v9 (fwd=32, 逆なし, CPU) | **6.946** |
| v10 fwd=16 / back=8 | 7.168 |
| v10 fwd=32 / back=4 | 7.201 (2026-06-30) |
| v10 **順方向のみ fwd=128**(GPU, 逆なし) | **7.127** (2026-06-30) |

→ **fwd=32 は v9 と同じシード数**。それでも 7.201 で v9 に届かない=v9との差は「逆方向を足したこと」だけ。
**「fwd=16 が交絡では?」の疑いは解消し、逆方向PFがLBを下げているとほぼ確定**(fwd16→7.168 より微悪化)。

**★順方向のみ128seed(GPU)= LB 7.127。特徴は v9 と完全一致を確認**(parquet列で照合: `artifacts_v10_3` と `artifacts_v9` はどちらも 511特徴・`pf_`164・`bpf_`/`cmp_`なしで同一集合)。
→ 差は **PF生成の作り方(CPU32seed×3 → GPU128seed×3, `pf_z`はCPUのまま)だけ**。それでも v9(6.946)に届かず 7.127。
**= 同一特徴でも前向きPFの生成(GPU化/シード)だけで LB が ~0.18 動く＝シード/生成のばらつきが大きい**(ユーザー所感: 「シードが良かっただけかも」と整合)。
PFパラメータ過学習・生成ばらつき仮説を補強。 [[v10-backward-pf-helps]]

## 順方向のみ版(切り分け用, 128シード)
- LB悪化(7.168)の切り分け: 逆方向が原因か / 順方向のシード数(v10は16, v9は32)が原因かを分離する。
- `create_train_parquet_v10.py` の **`BUILD_BACKWARD=False`** で逆方向(bpf_/cmp_)をスキップ=順方向特徴のみ生成。
  - 設定: `BUILD_BACKWARD=False`, `FWD_SEEDS=128`, `OUT_PARQUET` を別パス(例 `artifacts_v10_fwd/data/train.parquet`)。
  - 学習: train_models_v10 の `CFG.artifacts_path` をそのパスに。特徴選択は cmp_ 除外のまま(bpf_ が無いので自動的に順方向のみ)。
  - 提出: submit_v10 で `BUILD_BACKWARD=False`, `FWD_SEEDS=128`, `models_path` を順方向版に。
- 期待: 順方向のみ(128seed)LBが v9(6.946)並みに戻れば「逆方向がLBを下げた」、戻らなければ「順方向の作り(seed数/GPU)」要因。

## Kaggle 提出フロー(v9と同じ:ローカル学習→Kaggleで推論のみ)
- **(ローカル) [v10/train_models_v10.ipynb](../v10/train_models_v10.ipynb)**
  - v10 train.parquet を読み、LightGBM/CatBoost/XGBoost ×3(v9と同じパラメータ・koolbox.Trainer)を学習し
    `artifacts_v10_2/models/{lightgbm,catboost,xgboost}-1..3/` に保存。`pp_params={alpha:1, tau:85, w_pf:0.09}`。
  - **使用特徴 = 順方向 + 逆方向(bpf_)のみ。比較特徴(cmp_)は除外**(`cmp_` は有害だったため)。
    提出ノートは各Trainerの学習時特徴量リストに自動追従するので、submit側の変更は不要。
- **(Kaggle) [v10/submit_v10.ipynb](../v10/submit_v10.ipynb)**
  - **test 特徴量を GPU PF(v10パイプライン=`build_v10_dataset(split="test")`)で構築**(順方向GPU注入+逆方向bpf/cmp)。
  - 9モデルをロード → 平均アンサンブル → 補正(`apply_pp` + `sg_smooth`、v9と同一)→ `submission.csv`。
  - 必要な input データセット: コンペデータ / `create_train_parquet_v10.py` / v9特徴ノート(.ipynb) / 学習済みmodels / koolbox。
  - ★ test特徴は**学習時と同じPF設定(N_PF_SETS/FWD_SEEDS/BWD_PER_SEED)**で作る(列一致のため)。

## CV / 評価
- **GroupKFold(5) by `well`**(同一坑井の行が train/valid に跨るリーク防止)。
- **overall RMSE**(全OOF行プール)で比較。`target = TVT - last_tvt` なので target上RMSE = TVT上RMSE。
- 参考に坑井平均RMSEも出すが、Kaggle指標は overall。

## 結果(CV, GroupKFold(5) by well, overall RMSE)
- (1) 順方向のみ(=v9, 511特徴): **overall 7.9914**(坑井平均 6.0911)
- (2) 順方向+逆方向(627特徴): **overall 7.5537**(坑井平均 5.7349)→ **Δ=-0.438、逆方向が明確に効く**
- (3) +比較特徴: 不採用(cmp_ は有害)
- **提出用モデル(順方向+逆方向, cmp除外, fwd=16/back=8, 3PFセット)**:
  LGBM/CatBoost/XGB ×3 の **9モデルアンサンブル OOF RMSE = 7.5753**(補正前)。
  models → `artifacts_v10_2/models/`。LB は提出後に [scores.md](scores.md) へ追記。
- 所感:
  - 逆方向PF特徴 `bpf_*` の追加で overall・坑井平均ともに安定改善。[[v10-backward-pf-helps]]
  - fold4 が外れ値(9.8/9.2)で overall を押し上げ。長い/難しい坑井の塊か。
  - 参考: v12(1D-TCN, 同データ)は overall 7.871。LGBM単独より弱いが系統が違うのでブレンド候補。

## メモ
- 学習NBの `DEVICE_TYPE` は既定 "cpu"。GPU対応 LightGBM があれば "gpu"。
- 順方向PF特徴は GPU アンサンブルを build_well に注入して生成(`run_pf_ancc` をモンキーパッチ)。
  非PF特徴と `pf_z` は v9 CPU のまま。CPUでの順方向PF二重計算は無し。
