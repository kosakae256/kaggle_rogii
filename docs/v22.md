# v22 — 多scale 尤度加重アンサンブル(run_pf_lik_ensemble_scales 相当)の実験

> 7.191 の selector PF アルゴリズムを v20 GPU PF で実装し、scale(温度)・選択戦略・seed数を実験する。
> PFパラメータは r0/v20 のまま(触らない)。最終更新: 2026-07-01

## 仮説 / 狙い
- PFを多シード→**尤度で加重平均**→**複数の鋭さ(scale)**で出す→selectorで選ぶ、という構造の各レバーを切り分ける。
- (1) scale別精度(鋭い=最尤に賭ける/緩い=hedge, easy/hard別)
- (2) oracle(坑井ごと最良scale=上限) vs 到達可能戦略(固定/簡易ルール)= **選択の壁**を定量化
- (3) seed数(8/16/32/64)= 多いほど正確か?(=安定性であって精度でない仮説の検証)

## 手法
- `v21_common.run_forward_scales`(GPU 1走行で per-seed→scale再加重)で `{pf_scale_X, pf_mean}` を生成。
- 評価は train真値で easy/hard/all overall RMSE。

## カテゴリ別 PFチューナー(6分割・各カテゴリ独立・再開可)
- selector の 6カテゴリ(`code = int(n_eval>4840) + 2*searchsorted((136.73,185.51), z_span)`)ごとに well を分け、
  各カテゴリで Optuna(物理PF, GPU)で overall RMSE を最小化 → **6つのPFパラメータ**を得る。
- **残差ブースティング無し**(間違えた well の再チューニングはしない)。各カテゴリ独立。
- **再開可**: Optuna SQLite(`artifacts_v22/optuna.db`, study=cat{code}, trial単位)＋ `state.json`(完了codeスキップ)。
- エンジン(PF/GPU)は v19 と同一。出力 `artifacts_v22/per_category_pf.json`(code→最良パラメータ＋閾値同梱)。
- 実行: `.venv/Scripts/python.exe v22/tune_pf_per_category_v22.py`。CONFIG: `N_TRIALS=250`/カテゴリ, `SEARCH_SEEDS=8`/`EVAL_SEEDS=32`。

### 所感(効いた/効かなかった)
- **cat4(51本, 短×急傾斜=高z_span)が 11.79 で突出**(他6.5〜8.5)。**scale選択もほぼ無力**(scale_12で-0.008のみ)。
  → cat4の誤差は hedge/scale で減らない。**幾何(急dip)・dip外挿の失敗そのもの**＝硬い核([[hard_wells]])。**最優先の別対処が要る**。
- **scale選択は "カテゴリ級" なら安全に −0.105**。効くのは **cat3(長×中z, soft scale_20 −0.22)** と **cat5(長×高z, sharp scale_5 −0.17)**。カテゴリで最適scaleが違う(hedge寄り/commit寄りが分かれる)。
- **pf_ancc(調整済み likelihood_scale)が固定scaleより強い** → likelihood_scaleのチューニングは効いている。ただし percat級の出し分けでさらに僅かに乗る。
- **len-rule(非学習)は逆に悪化(+0.105)** = 素朴な長さルールは害。scale出し分けは"学習した(train上ベスト)"必要がある。
- oracle 7.50(−0.835)の伸びしろはあるが、**per-well選択は過去 mean に負けた履歴**([[v19-pf-bank-boosting]])＝到達可能性は別。percat級(6択)は低リスクで取れる分。
- 教訓: v21_common経路で評価すると v22調整の真価より悪く見える(pool 9.17 vs 正 8.34)。**評価は生成と同一エンジンで行うこと**。
