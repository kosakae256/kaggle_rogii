# v35 — v34モード構造特徴のGBM還流(シフト後処理→特徴量への変換)

> **状態: 実装済(未実行)。** ファイル: `v35/make_v35_parquet.py` → `v35/train_models_v35.ipynb`。
> 位置づけ: v32でLB逆噴射した「井戸レベルシフト後処理」の情報を、**v27→v28で実証済みの
> 「混ぜずに特徴化」変換**でGBMに入れ直す。v34ゲート(submit_v34)の転移リスクに対する保険でもある。

## 仮説
v34で見つけた信号(seed事後質量の分離 AUC 0.94、物理特徴)は本物。死んだのは「後処理シフト」という
使い方であって情報ではない。行単位の連続的な重み付け(GBM特徴)に変換すれば v28型の比例転移が期待できる。

## ★設計の要: 参照点は blend ではなくコンセンサス
v33/v34 の特徴は「blend(自分のOOF予測)からのズレ」で定義されていた。これをそのまま特徴にすると
**自分の完成予測を参照する v24型スタッキング**になり転移しない。v35では参照点を
**576本の per-seed 軌跡の行別 median(コンセンサス軌跡)= モデル非依存**に張り替えた。
モード構造(数・間隔・質量配分)は参照点の平行移動に不変なので情報は保たれる。

## 特徴(m34_ prefix, 18列)— すべて既存アーティファクトから再計算なしで生成
**行レベル(5)**: `m34_cons`(コンセンサス軌跡=全ソース統合の新PF列)/ `m34_cons_delta`(−lk)/
`m34_lo`/`m34_hi`(p10/p90−cons=双峰エンベロープの非対称)/ `m34_spread`(p90−p10)

**井戸レベル(13)**: `m34_n_modes` / `m34_minor_mass`(少数派の総質量)/
`m34_m2_c`・`m34_m2_mass`・`m34_mode_gap`(挑戦者モードの位置・質量・峰間)/
`m34_m2_{ext,tw,sm,fw}_mass`(挑戦者を支持する族)/ `m34_m2_xm_{self,nbr}`(挑戦者軌跡のGR採点マージン)/
`m34_m2_jump`・`m34_m2_rough`(挑戦者の物理)

## 使い回し(再計算ゼロ)
- v28の557列 → parquetに**列追記**(pyarrow, v30 r1と同方式)
- per-seed軌跡・grid・md/z → 実行済み `v34/artifacts_v34/seed_dump_pf{1,2,3}.npz`
- NN → 再学習なし。`nn_oof_combo` とのブレンド重み再探索のみ
- 新規計算 = **GBM 9モデルの再学習だけ**

## 実行手順
1. `python v35/make_v35_parquet.py`(数分・CPU)→ `v35/artifacts_v35/data/train.parquet`
2. **`python v35/add_lrn_v35.py`(~1分)** — d_metaランカーの集約軌跡を3列追記(2026-07-07追加):
   `m34_lrn`(softmax β1.0加重平均軌跡)/ `m34_lrn_delta`(−lk)/ **`m34_lrn_vs_cons`(−cons=
   ランカーが直した「形」成分の分離列。調査でlrnの価値はdatumでなく形と判明したためこれが本体)**。
   前提: `v34/artifacts_v34/q_d_meta_full.parquet`(labカーネルから保存したOOF q̂)。リークなし。
   ※列追記後は `artifacts_v35/models` を削除してから学習(特徴数変更でfold pklキャッシュ無効)。
3. `v35/train_models_v35.ipynb` を実行(v28学習のコピー、ART差し替え+m34 originトグル追加)
4. 末尾セルが NN(combo) ブレンドと、**旧v28 GBM×NN を同一行(ROW_FRAC間引き)で再計算した公平基準**を並べて表示
- 注意(test側): m34_lrn を提出に載せるには d_meta TCN の full-train 学習+提出ノートへのチャネル計算移植が必要
  (m34_cons等と違い学習器を伴う)。CVで効きを確認してから判断。

## 判定
- 公平基準(旧GBM×NN, 同一行)との Δ で見る(全行の 6.8711 とは行間引きの分だけ絶対値がずれる)。
- 効かなければ m34 origin を切って ablation(USE_ORIGIN["m34"]=False)。
- 効けば test 側へ: 列計算は submit_v34 の `_V34_SEED/_V34_META` 捕捉をそのまま流用して移植できる。

## 結果(2026-07-07)
**★CV明らかに悪化 → 学習途中で打ち切り(ユーザー判断)。** m34特徴入りGBMは素のfold RMSEの時点で
明確に劣化。

### 敗因の仮説(未検証)
1. **井戸レベル定数列(13本)の過学習が本命**: m34_m2_c / mass / 族別質量などは井戸内で全行同じ値。
   ツリーは「この定数の組合せ=この井戸」を実質井戸IDのように使い、train井戸の癖にフィットできる
   (GroupKFoldでもラベル直リークは無いが、汎化しない分岐が増える)。PFパラメータ列を増やすと悪化した
   教訓と同族。
2. 行レベル列(m34_cons系)はpf_ancc系と高相関で純増情報が薄く、1のマイナスを相殺できなかった。
3. lrn列も同様(datum情報はconsと同族と判明済み)。

### 次の切り分け候補(安い順)
- **行レベル8列だけ残す再試行**(m34_cons/cons_delta/lo/hi/spread + lrn/lrn_delta/lrn_vs_cons、
  井戸レベル定数13列を落とす)— ノートに M34_ROW_ONLY トグルを足すだけ。
- それでもダメなら m34系はGBM還流を撤退し、モードゲート(v34, LB5.930実証済)専用の信号として扱う。
