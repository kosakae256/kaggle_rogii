# v47 — 選択 Transformer(候補トークン × 2軸注意 + GR/struct/mode 証拠)

> **状態: 実装済・スモーク通過(本学習は未=ユーザー実行)。PF再生成は不要。**
> `v47/build_candidates_v47.py`(データ準備)/ `v47/train_selector_v47.ipynb`(学習・可視化)。

## 仮説
生成済み21候補(pf1/2/3·r0/r1/r4·pfA × tw/self/nbr)は **行ごと oracle≈2.14**。良い候補は既にある=**問題は選択**。
初版(候補スカラーを潰した soft選択)は OOF **6.485**(mean7.14/best単体7.60は超えたが oracle には遠い)。
→ 「モデルに**選択の根拠**を与えれば 4.x を狙える」というユーザー仮説を、特徴強化＋定式化変更で検証する。

## 変更点(初版 → 強化版)
1. **候補を"トークン"化**(スカラー21を1ベクトルに潰さない)。各候補トークン=根拠特徴14次元:
   `delta, log std, GR整合コスト(局所/広域), 符号misfit, mode位置(中央値差/符号), GRコスト順位, struct一致, 曲率`
   + 行共有文脈(md_since, nbr_has, nbr_nndist, struct sig)+ **候補identity埋め込み**(bank/flavor)。
2. **2軸注意 Transformer**(axial): **候補軸**(行内21で証拠を突き合わせ)＋**時間軸**(binでdatum枝の連続性)。
3. **尖った選択**: softmax温度 `TEMP=0.7` + **oracle-best への補助CE**(`AUX_CE=0.3`)。凸結合は保持(転移安全)。
4. **可視化**: 例示坑井で「候補パス＋選択(重み付き)＋真値」「**GR整合コスト×候補ヒートマップ**＋選択/oracle」を描画し、
   選択の"根拠"を目視(`v47_viz_well*.png`)。

## 追加した証拠特徴(★PF再生成なしで作成)
`build_candidates_v47.py` が既存候補＋**公式CSVのGR**＋既存structから算出し npz に格納(他バージョン非参照は維持):
- **GR整合コスト** `GRC/GRC2` = 窓平均 `|g_horizontal − f_typewell(TVT_k)|`(局所W21/広域W81)。**小=候補kの位置がGRと合う根拠**。
- 符号 misfit `GRM`(上/下ずれ)。
- **struct(K16)** `STRD=struct_tvt−lk` / `STRS=sig`(既存 pkl を取り込み)。
- 診断: **GR整合コスト単独(argmin貪欲)は 10.8**(=bimodal で弱い)。oracle一致率9%。
  → GR単独では選べない。**transformer が GR×時間連続×モード合意×struct を統合**して初めて効く、という設計。

## メモリ対策(GPU OOM / PC重負荷 → 解決, 2026-07-09)
初版強化モデルは**坑井まるごと**(最大~500bin×候補21)を2軸注意に入れて **GPU OOM**、npz全load＋並べ替え複製＋
評価の per-well `np.where`(773回)で **PC重負荷**だった。バッチ縮小では直らない(主因は系列長とRAM)。対策:
- **固定長チャンク `T_MAX=96 bin`**: 系列を切ってメモリ上限を固定(バッチ非依存)。GroupKFoldは坑井単位維持。
- **軽量モデル**(d64・2層・4head, 0.1M)＋ **AMP(fp16)** ＋ `set_per_process_memory_fraction(0.85)`。
- 構築後に中間配列(order複製等)を **明示解放**、評価SGは **argsortスライス**で高速化。
- 実測 **ピークVRAM 0.99GB**・~1-3s/epoch(60坑井)。フル773坑井でも安全に回る。

## ★潜在モードHMM(datum枝の確率的分類)= 最有力の次手 `train_mode_hmm_v47.ipynb`
soft凸結合が 6.4 で頭打ちなのは **bimodal を平均→2枝の中間に落ちる**構造的失敗(回帰の宿命)。
→ **回帰をやめ「どの datum枝か」を確率分類**する(ユーザー着想「分類問題にする」)。
- **モード定義**: 候補21を delta順に **K=3枝(下/中/上=各7候補)** に分割。`mode_rep[t,k]`=枝内平均。
- **天井(枝を当てられたら)**: K=2→4.45 / **K=3→3.55** / K=7→2.61。**mode_rep単体最良は6.83**(=常に1枝=mean級)
  → **価値は完全に「位置ごとにどの枝かを分類する」ことにある**。K=3 が学習性と天井のバランス最良。
- **モデル**: Encoder(1軸Transformer)→ 各位置で枝スコア(emission)。**sticky な線形鎖CRF/HMM**
  (対角初期化=枝はめったに乗り換えない + 連続性 |mode_rep差|)。forward-backward で **P(枝|全証拠)**。
  予測=確信区間は枝に commit(分類)/曖昧は確率hedge。学習=gold枝NLL+soft-MSE。推論=soft周辺/Viterbi両方。
- **証拠**: 各枝の GR整合(枝がGRに合うか)・struct一致・std・spread → emission。= v33 mode-gate(AUC0.82)/v42 struct vote(-6.6ft)の系列・確率版。
- 検証: メモリ安全(**VRAM 0.08GB**)、通し動作OK。スモークは未収束で判定不能=**フル学習で天井3.55にどこまで寄るかが本番**。
- 実行: `python は不要、ノートを実行`(env `V47_K`=枝数, `V47_EPOCHS`等)。他バージョン非参照。

## ★方法探索ループ(反復1-9, 2026-07-09)= `v47/explore*_v47.py`
「軽く実装→検証→次」で未検証手法を探索。**結論: PF候補の後処理は ~6.0 が実用天井、モードHMM soft=6.06 が最良。**
- **全手法台帳(overall RMSE)**: **モードHMM soft 6.06** > stacking4本 6.02(誤差) > seltok 6.38 > token 6.59 > CRF21状態 6.81 > LightGBM回帰 6.91 > mean 7.14。全予測 0.98 相関(stacking無意味)。
- **枝判別の情報天井(硬い行 acc~0.54)**: GR振幅(反1) / 時間sticky(反2 +0.005) / GR波形相関(反3 +0.007) / 空間近傍(反4 負) / 生GR CNN(反6 0.39≈チャンス) / 既知帯(反7 corr0.03)—**全軸で失敗**。
- **誤差の構造(反5)**: >10ft誤差の13%行がRMSEの72%。硬い行の枝は原理的に曖昧(annotation天井3.5と整合)。
- **易しい行(反8)**: LightGBM回帰でも 3.82=mean(oracle1.84不達)=within-branch余地も死。
- **勝因**: モード分類(K=3枝)× 系列 × sticky × end-to-end学習。per-row(LightGBM)54%頭打ちを、系列emission+soft posteriorが 6.06 まで押し下げた。Viterbi(hard)6.59<soft(soft生/hard死)。
- **唯一の未踏フロンティア**: 生GRマッチ画像で end-to-end(hengck23路線, [[hengck23-ceiling-formulation]])。反復6(1D残差CNN)は否定的だが2D全画像・パス生成jointは未検証=v48級。
